## 本轮改动

- 两个实际分布式rank分别承担不同窗口的生成、评分和反向计算；每rank独立冻结Judge、端口、实例标识、显存保护与日志。
- 同用answerability checkpoint-340的S4与A4合并为最多8个评分请求，候选和条件显式绑定；实际KV抢占增加后后续评分批退到4请求，不删除请求或改变G4。
- 四线程有序CPU读图/解码，下一Judge阶段准备与当前GPU评分重叠，记录预取剩余等待和真实阶段耗时。
- 每rank最多2GiB的冻结视觉CPU特征缓存；实际像素、grid、精度、冻结状态和随机性等匹配才复用，不安全时旁路，不缓存语言LoRA相关KV。
- 600训练条件按相近长度的不同窗口配对，seed42打乱pair顺序并均衡rank；原600/120条件集合不变。
- 裁剪和AdamW前显式求全部LoRA梯度的双卡均值，保留更新后全参数一致性检查；没有用事后权重广播掩盖失步。
- Guard只在主线程安全边界重建，避免后台重建把同进程主训练的并发显存分配误归因给自身。保留16MiB allocated/reserved预算、8GiB余量、85%目标和实时让步，每卡只有一套Guard。
- 完整断点恢复核查全局步数、原调度horizon、学习率、optimizer状态、双rank原生RNG和首对实际采样位置，保留真实历史评分前缀但不回放旧QA训练。
- Judge采用包内完整导入，启动异常及时落盘并由父进程检测，避免加载失败后等待健康检查超时。

## 目录与使用边界

`runtime/`保留当时私有运行根的相对结构：顶层双卡辅助模块、`multi-user/training/grpo_v3/six_user_binary/`实际包源码，以及`hpc/shared/`设备识别/保护依赖。顶层与包内同名文件是原运行布局的一部分，未为归档进行导入重构。

这是与现有仓库和Torch环境配套的源码快照，不是任意机器的一键训练包。`runtime/submit_speed.py`包含本次私有scratch路径、历史JobID和防重复提交检查；**不要在当前活动实验中再次执行它，也不要直接在新机器照搬路径后提交。** 归档代码不授权新增实验、扩大预算或恢复旧的第二学习率任务。

若以后要复现，应先在新的独立私有根准备仓库源码，再按`runtime/`相对路径覆盖本快照，提供实际数据、模型、Judge适配器、环境及配置。新环境的资源与路径需重新核验。本次上传没有修改当前活动Torch根或原工作区分支。

只运行轻量CPU回归：

```powershell
python multi-user/training/grpo_v3/experiments/full120_ftjudge_dual_speed_20261016/run_cpu_regressions.py
```

入口设置CUDA不可见，运行合批映射、解码顺序、预取复用、KV回退、长度配对、包内导入、Guard预算与断点恢复回归。不加载真实模型、不调用GPU、不执行sbatch。`runtime/test_gradient_sync_cpu.py`是另行使用真实Torch/Gloo两个CPU进程的测试，不包含在轻量入口中；原正式提交前已在Torch CPU环境完成对应回归，未把CPU测试冒充GPU检查。
